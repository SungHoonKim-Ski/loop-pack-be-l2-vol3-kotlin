# 실시간 랭킹은 없다
---
## 우리가 보는 순위는 이미 과거다

## "30분 전"

무신사를 열었다. 실시간 랭킹 탭에 "30분 전", "16분 전" 같은 표기가 붙어 있었다.

오늘의집도 마찬가지였다. "2026.04.10 04:56 기준"이라고 적혀 있다.


"실시간"이라는 단어를 쓰면서 왜 갱신 시점을 명시할까. 지금 이 순간의 데이터가 아니라는 뜻 아닌가.

> "실시간"이라고 적혀 있는 랭킹이 정말 지금 이 순간의 데이터일까?

아니다. 그리고 이건 버그가 아니라 **설계**다.

커머스 프로젝트에서 Redis Sorted Set 기반 랭킹 시스템을 구현하면서 이 사실을 체감했다. DB로 충분할 거라고 생각했던 초기 판단이 부하 테스트에서 어떻게 깨졌는지, 그리고 왜 빅테크가 준실시간이라는 선택지를 가져가는지를 정리한다.

---

## DB로 충분하지 않을까

처음엔 단순하게 생각했다.

사용자 행동이 쌓이는 `user_action_log` 테이블을 만들고 집계 쿼리를 요청하면 된다.

GROUP BY, ORDER BY. SQL 한 방이면 끝난다.

문제는 트래픽이다.

- 매 요청마다 full-scan에 가까운 집계 쿼리가 돌아간다
- 쓰기(INSERT)와 읽기(SELECT GROUP BY)가 같은 테이블을 사용한다
- 트래픽이 늘어나면 같은 데이터에 동시 접근이 몰려 **락 경합**이 발생한다
- DB 커넥션 풀이 고갈될 가능성이 있다.

"조회 한 번이 무겁지 않으면 괜찮지 않나?"라고 생각했다. 그리고 **한 번**은 괜찮다. 하지만 동시에 500명이 랭킹 페이지를 열면 이야기가 달라진다.

이 가설은 부하 테스트에서 확인했다. 결과는 뒤에서 다룬다.

---

## 왜 Redis Sorted Set인가

Redis의 Sorted Set(ZSET)은 skip list와 hash table의 조합이다.

핵심 연산의 시간복잡도는 이렇다:

- **ZINCRBY**: O(log N) - 점수 누적. 상품의 기존 점수에 더한다.
- **ZREVRANGE**: O(log N + M) - Top-N 조회. 점수 높은 순으로 M개를 꺼낸다.
- **ZCARD**: O(1) - 전체 수.

DB에서 같은 작업을 하면 어떤가.

```
DB: UPDATE product_metrics SET score = score + 0.1 WHERE product_id = 123
→ row-level lock 필요
→ 동시에 같은 상품에 조회 이벤트가 몰리면 lock wait 발생

Redis: ZINCRBY ranking:all:20260410 0.1 "123"
→ 단일 스레드에서 원자적 수행
→ lock 자체가 없다
```

**Redis는 단일 스레드다.** 이게 단점처럼 들리지만, ZINCRBY 같은 연산에서는 오히려 장점이 된다. 별도의 락 없이 원자적으로 점수를 갱신할 수 있다. DB에서는 같은 row에 대한 동시 UPDATE가 락 경합을 유발하지만, Redis에서는 구조적으로 불가능하다.

그래서 역할을 나눴다.

```
DB: 영속성 담당
→ user_action_log 테이블에 사용자 행동 기록 (감사 로그)

Redis: 집계 담당
→ ranking:all:{yyyyMMdd} ZSET에 실시간 점수 누적
```

DB는 "무슨 일이 있었는지"를 기록하고, Redis는 "지금 순위가 어떤지"를 계산한다. 관심사가 다르다. 실시간 점수 누적은 Redis가 흡수하고, DB에는 Kafka를 통해 이벤트가 비동기로 기록된다. DB에 가해지던 실시간 쓰기 부하가 Redis로 옮겨가고, DB는 결과적 정합성만 보장하면 된다.

---

## 하지만 "실시간"은 아니다

Redis에 점수가 쌓이는 과정을 따라가 보면 이렇다.

```
사용자가 상품을 조회한다
→ 서버가 이 행동을 이벤트로 기록한다
→ 이벤트가 메시지 큐(Kafka)를 거쳐 전달된다
→ 별도 소비자가 이벤트를 모아서 한 번에 Redis에 반영한다
```

각 단계마다 지연이 있다. 이벤트 발행에 수ms, 메시지 큐 전달에 수백ms ~ 수초, 소비자의 배치 대기에 수백ms. **총 지연: 수백ms ~ 수초.** 메시지 큐가 쓰기 폭증을 흡수하는 버퍼 역할을 하기 때문에 의도된 지연이다.

사용자가 상품을 조회한 시점과 그 조회가 랭킹에 반영되는 시점 사이에 간극이 있다. 이미 "실시간"이 아니다.

그런데 더 중요한 문제가 있다. Redis에 점수가 반영된 이후에도, **사용자가 랭킹 API를 호출하는 시점**에서 또 다른 선택지가 생긴다.

---

## 네 가지 읽기 전략

랭킹 데이터를 사용자에게 어떻게 보여줄 것인가. 네 가지를 비교했다.

### A. DB 직접 집계

매 요청마다 `user_action_log`에서 GROUP BY. 가장 단순하지만 가장 느리다.

### B. Redis ZSET 직접 조회

현재 구현. API 요청이 올 때마다 `ZREVRANGE`로 Redis에서 직접 조회한다. 충분히 빠르지만, 1000명이 동시에 같은 페이지를 요청하면 1000번 Redis를 조회한다.

### C. 결과 캐시 (TTL 60초)

Redis ZSET 결과를 로컬 인메모리에 캐싱한다. TTL 60초. 캐시가 살아있는 동안 Redis 연산 없이 즉시 응답한다.

> **이것이 "30분 전" 표기의 정체가 아닐까.** 무신사와 오늘의집이 보여주는 랭킹도 이와 비슷한 구조로, 마지막 캐시 갱신 시점의 스냅샷일 가능성이 높다.

### D. Singleflight 패턴

Go의 `singleflight.Group`에서 영감을 받았다. 동일한 키에 대한 동시 요청 중 **1개만 실제 Redis 조회를 수행**하고, 나머지는 그 결과를 공유한다.

```
1000명 동시 요청
→ 첫 번째 요청: Redis ZREVRANGE 수행
→ 나머지 999명: 첫 번째 요청의 CompletableFuture에 합류
→ 결과 반환: 1000명 모두 같은 응답
```

C보다 데이터가 더 최신이고(캐시 TTL이 아니라 요청 시점에 조회), B보다 Redis 부하가 낮다.

## 부하 테스트: 말보다 숫자

k6로 6개 시나리오를 돌렸다. 각 시나리오는 ramping-vus로 50→200→500 VU까지 올리고 90초간 유지했다.

### 테스트 환경

- Redis ZSET에 500개 상품, DB user_action_log에 약 8,000건 사전 적재
- DB 커넥션 풀: max=50
- Spring Boot + Virtual Threads

### 지연 허용치별 비교

| 시나리오 | 데이터 지연 허용치 | p50 | p95 | max | 에러율 |
|----------|-----------|-----|-----|-----|--------|
| A: DB 직접 | - | 557ms | 2,125ms | 3,179ms | 0.1% |
| B: Redis ZSET | 0s (실시간) | 312ms | 824ms | 2,542ms | 0.0% |
| C-5: 로컬 캐시 5초 | 5s | 47ms | 283ms | 2,364ms | 0.0% |
| C-60: 로컬 캐시 60초 | 60s | **18ms** | **182ms** | 883ms | **0.0%** |
| D: Singleflight | ~ms | 219ms | 711ms | 2,512ms | 0.0% |
| H: Local(5s)+Singleflight | 5s+SF | **29ms** | 245ms | **1,386ms** | **0.0%** |

### 결과 분석

**A vs B**: DB 직접 집계는 p50=557ms로 Redis(312ms)의 1.8배. 에러율도 0.1% vs 0.0%. GROUP BY + ORDER BY가 매 요청마다 수천 건을 스캔하기 때문이다.

**C-5 vs C-60**: 데이터 지연 허용치를 5초에서 60초로 늘리면 p50이 47ms → 18ms로 **2.6배 빨라진다.** 캐시 hit율이 올라가기 때문이다. 하지만 max는 2,364ms → 883ms로 차이가 더 극적이다. TTL이 짧으면 cache miss가 자주 발생하고, miss마다 Redis ZREVRANGE + product enrichment 비용을 부담한다.

> 데이터 지연 허용치를 늘리면 성능이 좋아진다. 무신사가 "30분 전"을, 오늘의집이 갱신 시각을 표기하는 것도 이런 맥락이 아닐까 생각한다.

**D: Singleflight는 캐시 없이 가장 효율적이다.** p50=219ms로 Redis 직접(312ms)보다 빠르고, 에러율 0.0%. 하지만 **단독으로는 캐시(18~47ms)에 비할 수 없다.** Singleflight의 진짜 역할은 다음이다.

**H: 하이브리드(로컬 캐시 5s + Singleflight)가 이 프로젝트에서 선택한 조합이다.**
- p50=29ms: C-5(47ms)보다 빠르다. 로컬 캐시 hit 시 0ms, miss 시 Singleflight가 중복 조회를 막으므로.
- max=1,386ms: C-5(2,364ms)보다 **1,000ms 낮다.** cache miss 순간의 캐시 스탬피드를 Singleflight가 방어한 결과다.
- p95=245ms: C-5(283ms)보다 낮다.

> Singleflight는 p50을 개선하는 게 아니라, **max와 p95를 개선한다.** 캐시가 비는 순간의 최악 시나리오를 방어하는 것이 핵심 역할이다.

## 콜드 스타트 - carry-over 10%

매일 자정이 되면 랭킹이 초기화된다. 어제까지 쌓인 점수는 어제 것이고, 오늘은 0점부터 다시 시작한다.

오전 6시에 앱을 연 사용자가 빈 랭킹을 보면 이상하다. 어제 인기 있던 상품이 오늘 아침에도 어느 정도 순위에 있어야 자연스럽다.

이를 위해 배치 작업을 만들었다.

```
매일 23:50 실행 (Spring Batch)

ZUNIONSTORE tomorrow = (tomorrow × 1.0) + (today × 0.1)
```

어제 점수의 **10%**를 오늘에 이월한다.

왜 10%인가.

- **100%**: 어제 인기 상품이 영원히 1위. 신상품이 치고 올라올 수 없다.
- **0%**: 매일 새벽 랭킹이 텅 비어있다.
- **10%**: **관성을 주되 역전 가능성을 보장**하는 균형점.

어제 1위였던 상품이 오늘 아무 활동이 없으면, 오늘 열심히 조회/주문되는 상품에 금세 밀린다. 하지만 오전 시간대에는 어제의 관성으로 빈 랭킹을 방지한다.

### 배치가 두 번 실행되면?

`ZUNIONSTORE`는 멱등하지 않다. 같은 날 두 번 실행되면 어제 점수의 10%가 20%로 누적된다.

```
1회 실행: today = (today × 1.0) + (yesterday × 0.1) → yesterday 10% 반영
2회 실행: today = (today × 1.0) + (yesterday × 0.1) → yesterday 20% 반영
```

Spring Batch의 `RunIdIncrementer`가 동일 파라미터 재실행을 막아주지만, 수동 실행이나 장애 복구 시 중복이 발생할 수 있다. 그래서 Redis에 `SET NX` flag를 두었다.

```
carry-over 실행 전:
  SET ranking:all:carry-over:{yyyyMMdd} "done" NX EX 172800

→ 이미 키가 있으면 (NX 실패) → 스킵
→ 키가 없으면 (NX 성공) → carry-over 실행
```

설계만 하면 끝이 아니다. 운영에서 "같은 작업이 두 번 실행되면 어떻게 되는가"를 항상 확인해야 한다.

## ORDER 점수의 log10 정규화

상품 조회는 0.1, 좋아요는 0.2로 단순하다. 문제는 주문이다.

만 원짜리 상품 주문과 백만 원짜리 상품 주문을 같은 0.7점으로 처리하면, 가격이라는 중요한 신호를 무시하게 된다. 그래서 금액을 반영하되, 로그 함수로 정규화했다.

```
score = 0.7 × log10(price × quantity + 1)

저가 주문: 10,000원 × 2개 = 20,000원 → log10(20001) ≈ 4.3 → 점수 ≈ 3.0
고가 주문: 1,000,000원 × 1개             → log10(1000001) ≈ 6.0 → 점수 ≈ 4.2
```

가격이 100배 차이나지만, 점수는 1.4배만 차이난다. 고가 상품이 랭킹을 독점하는 현상을 방지하면서도 금액의 영향을 반영한다.

## 양방향 backpressure

여기서 한 발 물러서 전체 그림을 보면 흥미로운 구조가 보인다.

```
쓰기 경로:
  초당 10,000건 이벤트 → Kafka batch → Redis ZINCRBY 200회/초

읽기 경로:
  초당 10,000건 조회 → 로컬 캐시 hit 99% → 글로벌 캐시 hit 0.9% → ZREVRANGE 1회/60초
```

Kafka가 "쓰기 폭증으로부터 Redis를 보호"하듯이, 캐시 레이어가 "읽기 폭증으로부터 Redis를 보호"한다. **양방향 backpressure**다.

Redis ZSET은 "진실의 원천"이지만, 직접 접근하는 빈도를 양쪽에서 극단적으로 줄인다. Redis가 빠르다고 해서 무한정 때리는 게 아니라, Redis도 보호 대상이다.

## 몇 초 전 데이터를 허용할 것인가

결국 모든 전략의 차이는 하나로 수렴한다.

> **"사용자에게 몇 초 전 데이터를 보여줄 것인가."**

이미 쓰기 경로에서 수초의 Kafka 지연이 있다. Redis ZSET에 있는 데이터 자체가 이미 과거다. 여기에 읽기 경로에서 얼마를 더할 것인지를 선택하는 문제다.

### 짧은 준실시간 (초 단위): Singleflight

```
데이터 지연 허용치: ~5초
방식: 요청이 오면 그때 Redis 조회. 동시 요청은 합쳐서 1번만.
갱신 트리거: 사용자 요청 (cache miss)
```

- 장점: 가장 신선한 데이터. 아무도 안 보면 계산도 안 한다.
- 단점: TTL 만료 순간 첫 사용자가 지연을 부담한다. **단일 인스턴스 내에서만 동작**한다. API 서버가 10대면 최대 10번의 Redis 조회가 발생한다.

### 긴 준실시간 (분~시간 단위): Scheduler

```
데이터 지연 허용치: 60초~1시간
방식: 백그라운드 스케줄러가 주기적으로 Redis 조회 후 결과 저장.
갱신 트리거: 시간 (cron / fixedRate)
```

- 장점: **사용자가 갱신 비용을 절대 안 본다.** 캐시는 항상 warm. 구현이 `@Scheduled` 한 줄이다.
- 단점: 아무도 안 봐도 계산한다. 데이터 지연 허용치를 짧게 가져가면 불필요한 Redis 부하가 발생한다.

### 비교

| 관점 | Singleflight (초 단위) | Scheduler (분~시간 단위) |
|------|----------------------|------------------------|
| 첫 요청 지연 | cold start 있음 | 없음 (항상 warm) |
| 데이터 지연 허용치 | 요청 시점에 따라 가변 | **예측 가능** (갱신 시점 표기) |
| 불필요한 계산 | 없음 | 있음 |
| 멀티 인스턴스 | 인스턴스마다 독립 | 글로벌 캐시 공유 |
| 구현 복잡도 | 동시성 처리 필요 | @Scheduled 한 줄 |

무신사의 "30분 전" 표기나 오늘의집의 갱신 시각을 보면, **Scheduler 방식에 가깝다고 추측한다.** 주기적으로 스케줄러가 랭킹을 조회하고 결과를 캐시에 저장한 뒤, 사용자는 그 스냅샷을 보는 구조일 것이다. 데이터 지연 허용치를 분 단위로 포기하는 대신, 인프라 부하를 극소화하는 전략이다.

## 프로덕션 하이브리드

둘 다 쓰면 된다.

```
로컬 캐시: Caffeine (인스턴스별, TTL 5초)
  → 직렬화 없이 객체 직접 반환. 가장 빠름.
  → 5초간 같은 인스턴스의 모든 요청이 0ms로 응답.

로컬 캐시 miss → Singleflight (인스턴스 내)
  → 같은 인스턴스에서 동시에 miss여도 1번만 글로벌 캐시 조회.

  → 글로벌 캐시: Redis String (TTL 60초)
    → Scheduler가 매 60초 선갱신. 인스턴스 10대가 공유.
    → 갱신 시점 표기("30분 전")의 레이어.

  글로벌 캐시 miss → ZREVRANGE 1번 실행, 글로벌 캐시에 저장.
```

이 구조에서 Redis ZSET 직접 조회는 **60초에 최대 1번**이다. 각 인스턴스는 **5초에 1번**만 글로벌 캐시를 조회한다. 나머지 요청은 **로컬 메모리에서 0ms**로 응답한다.

Singleflight가 단독으로 못 하는 것(멀티 인스턴스 보호)을 글로벌 캐시가 하고, Scheduler가 단독으로 못 하는 것(짧은 데이터 지연 허용치, long tail 페이지)을 Singleflight가 한다.

```
Scheduler: 메인 랭킹 (page 0~2) 선갱신 → 항상 warm
Singleflight: long tail (page 3+) → 요청 올 때만 계산
로컬 캐시 (Caffeine): 모든 페이지 → 5초간 인스턴스 내 재사용
```

## 정리 - "실시간"의 재정의

처음으로 돌아가자.

무신사가 "30분 전"이라고, 오늘의집이 갱신 시각을 표기하는 건 정직한 표기다. 그리고 그 뒤에는 이와 비슷한 구조가 있지 않을까 추측한다.

- **쓰기 경로**: Kafka가 이벤트 폭증을 흡수하여 Redis를 보호
- **읽기 경로**: 로컬 캐시(Caffeine) + 글로벌 캐시(Redis)가 조회 폭증을 흡수
- **데이터 지연 허용치 선택**: Scheduler로 메인 랭킹을 분 단위로, Singleflight로 long tail을 초 단위로

기술적으로 완전한 실시간 랭킹을 만들 수 있는가? 가능하다. 매 요청마다 Redis ZSET을 직접 조회하면 된다. 하지만 그걸 1000만 사용자에게 제공하면 Redis가 병목이 된다.

> "실시간"은 기술적 속성이 아니라 **지연 허용치**의 문제다. 쓰기 경로에서 이미 수초를 썼고, 읽기 경로에서 얼마를 더 쓸 것인가를 정하는 것이다.

무신사는 약 30분 단위를 선택한 것으로 보인다. 이 프로젝트는 5초~60초 하이브리드를 선택했다. 어느 쪽이 맞다고 할 수 없다. 트래픽 규모와 사용자 기대치에 따라 **지연 허용치를 배분**하는 것이고, 모든 선택에는 trade-off가 있다.

이번 구현에서 배운 건 하나다.

**"30분 전"이라는 표기는 타협이 아니라, 지연 허용치를 가장 효율적으로 쓴 결과다.**
