왜 캐시인가 — 모든 최적화의 출발점

DB는 왜 느리고, 캐시는 왜 빠른가

자주 읽는 결과를, 더 빠른 계층에 둔다.

DB가 (글로벌 캐시보다도) 느린 이유
디스크 본체
데이터가 디스크(SSD/HDD)에 있다 → Redis는 순수 메모리. (물리적 이유는 다음 장)
쿼리 실행 + 버퍼풀 한계
파싱·플래닝·실행이 매번 얹히고, InnoDB 버퍼풀(RAM)도 용량 한계 → 미스 시 디스크 random I/O. Redis는 키 조회 한 방.
네트워크도 '비용'이다
글로벌 캐시(Redis)든 DB든, 네트워크 너머라 요청-응답 왕복(~수백 µs)이 똑같이 든다 — DB만의 병목이 아니다. 로컬 캐시(Caffeine)만 이마저 없앤다.
그래서 — 캐시 계층의 선택

글로벌 캐시 (Redis)

디스크 + 쿼리 실행을 없앤다. 네트워크는 남지만 메모리 조회라 DB보다 빠르다. 여러 인스턴스가 공유.

로컬 캐시 (Caffeine)

네트워크 왕복마저 없앤다(~ns). 대신 인스턴스마다 사본이 따로 생긴다.

⚠ 일관성 지점이 늘어난다 — 무효화할 곳이 DB(1) → +글로벌 Redis(2) → +로컬 캐시 N대(2+N). 계층을 더할수록 갈라진 사본이 늘어 무효화가 어려워진다(로컬은 인스턴스 간 동기화가 사실상 불가 → 보통 짧은 TTL로 타협).
결과를 더 빠른 계층에 두는 한 가지 이야기 — 인덱스로 디스크 덜 읽기(P1)·캐시로 메모리에(P2)·사전계산으로 미리(P3).
잠깐, "랜덤 액세스"?

"랜덤 액세스라서" 빠른 게 아니다

흔한 오해 — 랜덤 액세스는 속도가 아니라 '접근 방식'을 가리키는 말이다.

① 랜덤 액세스 = 접근 방식
"임의 위치를 직접 지정 가능"이란 뜻. 반대말은 테이프식 순차 접근(10번 곡 들으려 1~9번을 감아야 함). CD가 10번을 바로 누르는 게 랜덤 — 속도와는 무관한 개념이다.
② RAM이 빠른 진짜 이유 = 전자식
전기 신호로 닿는다 → 나노초(ns). 디스크(HDD)는 금속 헤드가 물리적으로 이동해서 닿는다 → 밀리초(ms). 전기 신호 vs 기계 운동 — 이게 100만 배 차이의 본질.
③ 주소는 둘 다 안다
디스크도 "1234번 → 몇 트랙 몇 섹터"를 즉시 계산한다. 차이는 그 다음 — RAM은 데이터 주소 계산이 끝난 순간 데이터에 접근 가능하지만, 디스크는 헤드 이동 + 회전 대기 시간이 걸린다.
비유로

RAM = 책상 서랍

진짜 랜덤 액세스

몇 번 칸이든 손만 뻗으면 닿는다. "3번 칸"이라고 아는 순간 = 꺼낸 거나 마찬가지. 어디든 거의 똑같이 빠르다.

디스크 = 회전목마 책장

반쪽짜리

칸 번호를 알아도 바로 못 꺼낸다.
① 그 칸까지 걸어가고 (헤드 이동)
② 책장이 돌아 칸이 올 때까지 기다린다 (회전 대기)
→ 멀수록 느리다.

세 줄 요약 — ① 랜덤 액세스 = "임의 위치 직접 지정"(↔순차), 빠름이 아님 ② RAM은 전기로 닿아 빠르고, 디스크는 헤드가 움직여 느림 ③ 주소는 둘 다 안다 — 차이는 '아는 것'과 '닿는 것' 사이의 물리 운동.
SSD는 왜 RAM보다 느릴까

같은 전자식인데도, SSD가 RAM보다 느린 이유

영속성을 얻은 대가로 속도를 내줬다 — 4가지 이유.

① 셀 재질이 다르다
DRAM은 전하로 잠깐 담는다(물컵 붓고 비우기). NAND는 전자를 절연막에 가둬 비휘발성으로(금고에 잠그기) — 안 빠지게 가두니 넣고 빼기가 느리다.
② 덮어쓰기가 안 된다
쓰기는 페이지(4~16KB), 지우기는 더 큰 블록 단위. 한 글자 수정도 "블록 읽기 → 새로 쓰기 → 옛 블록 지우기"(가비지 컬렉션). 연필이 아니라 펜으로만 쓰는 공책.
③ 컨트롤러를 거친다
FTL(논리↔물리 주소 변환)·웨어레벨링(수명 분산)·GC를 하는 중간 관리자가 반드시 낀다. RAM엔 없는 계층.
④ 통로가 멀다
PCIe/SATA + OS 파일시스템·드라이버 소프트웨어 계층을 거친다. CPU와 버스로 직결된 RAM보다 단계가 많다.
삼각형 — 속도 vs 영속성
빠름·휘발  ◀───────▶  느림·영속
RAM ns · 가장 빠름 ✗ 휘발
전기 신호 · CPU 직결  |  한 글자도 바로 수정
SSD µs · 중간 ✓ 영속
전기(NAND) · 컨트롤러 + I/O 경유  |  블록 지우고 다시 써야
HDD ms · 가장 느림 ✓ 영속
금속 헤드 물리 이동  |  그 자리에 덮어쓰기
RAM은 속도를 얻고 영속성을 포기, 디스크는 영속성을 얻고 속도를 내줌. 그래서 계층으로 쌓는다 — 자주 쓰는 건 RAM(캐시), 영구 보관은 디스크.
DB들의 캐시, 공통 뼈대

DB도 캐시를 쓴다

같은 물리 제약(RAM vs 디스크)을 푸니 해법이 수렴한다 — 이름만 다를 뿐.

1 페이지 캐싱 Buffer Pool 계열
데이터·인덱스 페이지를 RAM에 들고 있어 디스크 I/O를 줄인다. "DB 메모리 튜닝 = 이 캐시 크기 잡기"
MySQL (InnoDB)Buffer Pool · 16KB
PostgreSQLShared Buffers · 8KB
OracleBuffer Cache · SGA
SQL ServerBuffer Pool
MongoDBWiredTiger Cache
SQLitePage Cache
2 쓰기는 WAL 먼저 Write-Ahead Logging
데이터 파일(디스크)에 바로 쓰면 여기저기 흩어진 랜덤 쓰기라 느리다. 그래서 ① RAM 버퍼에서 바꾸고 ② 변경분만 로그 끝에 순차로 이어 붙여(append=빠름) 영속성을 먼저 확보 — 데이터 파일은 나중에 모아서 반영하고, 장애가 나도 이 로그로 복구한다.
MySQL · Oracleredo log
PostgreSQLWAL · 원조
SQL Servertransaction log
MongoDBjournal
3 그 아래 OS page cache
DB 종류와 무관하게, 디스크 파일을 읽으면 OS가 한 번 더 캐싱한다. 같은 제약 → 같은 해법.
그럼 뭐가 다르고, 왜 Redis인가

다른 건 구현 디테일 — '결과 캐싱'은 빠졌다

DB마다 다른 부분
OS 캐시를 믿느냐, 직접 관리하느냐
PostgreSQL — shared_buffers 작게 + OS page cache에 위임(권장 ~25%). Oracle·InnoDB(O_DIRECT) — OS 우회, 자기 버퍼에 직접 관리(~50–70%). 같은 페이지 캐싱인데 역할 분담이 정반대.
교체 정책
다 LRU 계열이나 변형이 제각각 — InnoDB young/old(대량 스캔 오염 방지), PostgreSQL clock sweep. 목표는 같고 알고리즘이 다르다.
그래서 — 왜 Redis인가
결과 캐싱은 공통이 아니다
MySQL Query Cache는 8.0에서 제거(무효화·경합). 페이지 캐시는 디스크 I/O만 줄일 뿐, 파싱·플래닝·실행은 매번 → 현대 DB는 결과 캐싱을 앱(Redis)으로 외부화한다.
in-memory DB는 트레이드오프를 뒤집음
Redis·SAP HANA — "디스크가 본진, RAM이 캐시"가 아니라 RAM이 본진, 디스크는 백업(스냅샷·AOF)용. 속도 최우선, 용량은 RAM 한계.
공통 = 페이지 캐싱·WAL·OS 캐시. 다름 = OS 의존도·교체 정책·결과 캐싱. DB가 안 하는 결과 캐싱, 그 자리를 Redis가 채운다.

C1 · 인덱스로 정렬까지 끝내기

복합 인덱스커버링 인덱스EXPLAINfilesortleftmost prefixdescending(8.0)
① 복합 인덱스
여러 컬럼을 묶은 B+Tree. 리프에 컬럼 순서대로 정렬 저장 → 선두로 진입해 순차 스캔하면 그게 곧 정렬 결과(추가 정렬 0). 규칙: 등치(=) 필터 먼저, 정렬키 뒤. (leftmost — 왼쪽부터 연속으로 써야 먹는다)
② 커버링 인덱스
필요한 컬럼이 전부 인덱스 안에 있으면 PK 본체를 안 읽는다(Using index). SELECT *는 빠진 컬럼 때문에 행마다 PK lookup → 커버링 깨짐.
③ EXPLAIN
쿼리가 인덱스를 타는지 보는 창 — key(실제 쓴 인덱스), Extra(Using index=커버링 / Using filesort=재정렬)를 확인한다.
④ filesort
인덱스로 ORDER BY를 못 풀면 sort buffer(크면 디스크)에서 다시 정렬. LIMIT 20이어도 매칭 행 전체가 정렬 대상이라 비싸다 → 이게 안 뜨게 만드는 게 목표.
Before · 단독 인덱스
WHERE brand_id=? AND status='ACTIVE'
ORDER BY like_count DESC
-- EXPLAIN: Using where; Using filesort
After · 복합 인덱스
CREATE INDEX idx ON t
  (brand_id, status, like_count DESC, id DESC);
-- EXPLAIN: Using where  (filesort 제거)
id DESC tie-breaker로 커서(C2)와 호환. 함정 — like_count DESC, id ASC처럼 방향이 어긋나면 filesort 부활.

PART 2 · 캐싱

C3 · 같은 질문은 캐시로

cache-asidewrite-throughwrite-behind무효화 evict/TTL

읽기는 대개 cache-aside로 같지만, 쓰기를 어떻게 반영하느냐가 갈린다.

cache-aside 이 프로젝트
앱이 직접 다룬다. 읽기 — 캐시 먼저, miss면 DB 후 적재. 쓰기 — DB 갱신 후 캐시 무효화(evict/TTL). 가장 흔하다.
write-through
쓰기가 캐시를 거쳐 DB로 같이 간다. 캐시·DB가 항상 일치(강한 일관성). 대신 쓰기마다 두 곳을 써서 느리다.
write-behind (write-back)
쓰기는 캐시에만 먼저, DB는 나중에 비동기로 모아서. 쓰기 가장 빠름. 대신 반영 전 장애 시 유실 위험.
전략일관성쓰기위험
cache-aside보통 (잠깐 stale)빠름무효화 누락
write-through강 (항상 일치)느림—
write-behind약 (지연)가장 빠름장애 시 유실
이 프로젝트는 cache-aside — DB 갱신 후 무효화(상세·참조는 evict, 목록은 키 조합이 무한해 짧은 TTL). 강한 일관성보다 단순성·읽기 성능을 택한 선택.
PART 2 · 캐싱

C4 · 캐시가 죽어도 서비스는 산다

graceful degradationfallbackfail-open vs fail-closedMaster/Replica
graceful degradation
일부 구성요소가 죽어도 전체가 멈추지 않고 기능/성능만 일부 떨어지는 설계. 캐시를 도입하면 캐시가 새 의존성이 되므로, 그 장애를 서비스 장애와 분리해야 한다.
fail-open vs fail-closed
같은 "실패 처리"라도 방향이 정반대. 보조 장치(캐시)는 실패 시 통과(fail-open), 게이트(인증·결제)는 실패 시 차단(fail-closed)이 맞다.
읽기 분산
읽기는 Replica, 쓰기는 Master로 부하 분산. 대신 복제 지연(lag)으로 방금 쓴 값을 곧장 못 읽을 수 있다(캐시 특성상 보통 허용).

fail-open

실패 시 통과

캐시·추천·랭킹. Redis가 죽어도 DB로 fallback → 느려질 뿐 안 멈춤.

fail-closed

실패 시 차단

인증·권한·결제. 불확실하면 거부 — 통과시키면 사고.

늘어난 저장소의 비용

        
일관성

        
원본과 캐시가 어긋난다(stale). 무효화(evict/TTL)를 어떻게 할지가 따라붙는다 — 캐싱의 가장 어려운 문제.

        
미스 페널티

        
미스면 캐시 조회 + DB 조회 + 캐시 적재를 다 한다 → 히트율이 낮으면 오히려 느려진다. 캐시는 히트율이 전제.

        
메모리·eviction

        
캐시도 유한한 자원 → LRU/LFU 같은 퇴출 정책 필요. 무한히 담을 수 없다.

      

      

        
캐시 특유의 두 고질병

        

          
캐시 스탬피드

          
thundering herd

          
인기 키가 만료되는 그 순간 수백 요청이 동시에 미스 → 전부 DB로 몰린다.

        

        

          
콜드 스타트

          
cold cache

          
배포·Redis 재시작 직후 캐시가 비어 모든 요청이 미스 → DB 폭주.

        

        
둘 다 "빠르게 접근하려" 만든 캐시가 오히려 DB를 무너뜨리는 역설 → 그래서 캐시엔 전략이 필요하다.

      

    

  







  

    PART 2 · 캐시 스탬피드
    
캐시 스탬피드 — 만료 순간의 폭주

    

      

        
문제와 전략

        
문제

        
인기 키 하나가 만료되는 순간, 그 키를 기다리던 수백 요청이 동시에 미스 → 전부 DB로(thundering herd). 캐시가 있어도 만료 타이밍에 DB가 출렁인다.

        
전략 1 · 지터(jitter)

        
TTL에 랜덤을 더해 만료 시각을 흩어준다. 인기 키들이 같은 순간에 동시 만료되는 것을 막는다.

        
전략 2 · 싱글플라이트

        
같은 키 동시 요청 중 1개만 DB를 치고, 나머지는 그 결과를 기다린다. Go의 singleflight가 대표적 — 직접 구현 가능.

      

      

        
구현한다면 · code level

        

          
① 지터 TTL

          

        

        

          
② 싱글플라이트 (Go singleflight 직접 구현)

          

        

      

    

  







  

    PART 2 · 콜드 스타트
    
콜드 스타트 — 빈 캐시의 첫 순간

    

      

        
문제와 전략

        
문제

        
배포·스케일아웃·Redis 재시작 직후엔 캐시가 텅 비어 있다 → 모든 요청이 미스 → 트래픽이 그대로 DB로 쏟아진다. 가장 바쁜 오픈 직후에 가장 위험.

        
전략 1 · 워밍업(pre-warm)

        
오픈 전에 운영자/스크립트가 인기 데이터를 미리 적재한다. 트래픽이 들어오기 전에 캐시를 데워둔다.

        
전략 2 · 싱글플라이트

        
워밍업이 못 덮은 키도, 동시 미스를 1회 로딩으로 묶어 DB 폭주를 완화한다(스탬피드와 같은 도구).

        
랭킹처럼 기간 단위로 리셋되는 콜드 스타트는 전일 점수 일부를 이월(carry-over)해 따로 대응 — 같은 문제, 다른 결.

      

      

        
구현한다면 · code level

        

          
워밍업 — ApplicationRunner로 오픈 전 적재

          

        

        
스케일아웃마다 새 인스턴스가 콜드 → 워밍업을 부팅 훅에 두거나, Redis를 공유 캐시로 두면 인스턴스 추가의 콜드 영향을 줄인다.

      

    

  






  

    
그래서, 왜 느렸나

    
카드를 클릭 — DB가 왜 느렸고, 어떻게 풀었나

    

      

        

          
토대 · 왜 느린가
느린 계층을 덜 건드려라

          
DB는 디스크 본체 + 네트워크 왕복 + 쿼리 실행이라 느리다. 읽기 최적화 = 느린 계층을 덜 건드리는 일.
